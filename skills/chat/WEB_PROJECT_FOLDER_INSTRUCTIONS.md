# Web project folder instructions · KFB production

Paste this into the instruction field of a Web project/folder.

You are working on a bounded KFB production slice. Begin by reading the current GitHub versions of:

1. `skills/chat/START_HERE.md`
2. `skills/chat/CHAT_GITHUB_KFB_STAGE_WORKFLOW.md`
3. `skills/chat/FRESH_CHAT_SLICE_PROTOCOL.md`
4. the named project SSOT, current Recovery/Return and the slice briefing

GitHub state overrides chat memory. Work on one named owner, branch and product outcome. Name a Stage/public route only when the current project actually requires one. Reuse verified donors and existing modules before creating anything new. A loaded asset URL is not proof that the actual donor design was used; show the source object in isolation before integrating it. Do not introduce placeholders, generic UI chrome, replacement branding or a second runtime owner when a current source/owner already exists.

Persist at phase boundaries: coherent implementation milestone, material evidence/test milestone, then final Return/handoff. Do not write Return/Hub metadata after every small test. After every actual GitHub write, fetch the exact branch head and intended files. A timeout means UNKNOWN, not success: inspect the ref or workflow first and retry only if the write is absent.

Use the current project's named acceptance surface. For Site-capable products, GPT Site is primary. Use direct `https://kayfabizarro.pages.dev/…` only when a formal Cloudflare/public Stage is explicitly required. GitHub Pages, githack, raw-CDN and local file links are never final public acceptance surfaces. Do not claim a host as verified until its exact URL shows the expected revision.

Keep the owning project Return current. Update the additive changelog, central router or KFB Hub only when the result materially changes routing, a P0/human gate, or a canonical product/tool URL. Routine TODO/status changes stay in GitHub Issues/owner state and do not trigger Hub/Cloudflare work. Return exact repo/branch/PR/head, changed files, actual tests, relevant visible proof, unresolved items and one next gate; include a Stage/Site URL only when that surface was actually required. Do not auto-merge or promote Live without the named authority.

If an optional helper CLI such as `game-dev` is unavailable, record it once and continue with repository-native checks unless the brief specifically requires sealed Game Development Studio evidence. After two non-improving repair passes on the same gate, stop repairing the **smallest failing seam**, preserve/export that seam, and continue the parent outcome unless the Production Guard proves the seam is outcome-critical.
