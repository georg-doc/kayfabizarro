## Product outcome

One authentic KFB actor is modified in a **single diegetic Maker bench** through an already implemented specialist operation, produces a durable versioned configuration, survives close/reload and can be restored, without changing any global actor defaults. This is a production-workflow MVP, not an Island MVP, and not public Stage.

**One reliable before/after/reload is more valuable than a showroom of 20 static links.**

## Visual UX (cartoon grammar)

- Existing character clone standing at the workbench; source original unchanged.
- One visible current KFB tool/part donor, previewed separately before application.
- Existing EyeRig/FrankenStein module does the real operation; no generic face gizmo or UI component counted as an original.

## Real operations and phased feature gates

### Phase A · SOURCE-ISOLATE (mandatory; part of active visual gate)

A1. Select one actual actor source and version. If FrizzleBob v5b source pins conflict or its current authoring owner lacks a verified load, do not silently choose legacy Cube Pet or dummy. Instead use a separately owner-approved Rig_Medium fixture, report name/ref, and keep FrizzleBob source gate open.
A2. Separately show current actor and existing `headzones.v1`, `pet-eye-rig.v6`, or `facegraft.v1` donor path in original working context. Record exact source identity, screenshot and module version. A label/source URL without visual object is UNKNOWN.

### Phase B · FIRST ACTUAL EDIT (one simplest compatible seam)

Start with **sclera or pupil/head-zone color** using the existing `kfb.headzones/0.1` field, or an accepted EyeRig profile parameter, not arbitrary new nose geometry. Confirm actual before/after difference and rebuild survival. This tests the complete transaction with minimal geometry risk.

### Phase C · ROUNDTRIP VALIDATION

Existing tool owner exports actor-specific existing `kfb.pets/1` config and any already accepted eye/profile companion format. Preserve all unrelated fields exactly, including `null`, `false`, 0 and unknown extension fields. The MakerSpace **receipt is a sidecar, not a replacement schema**.

The minimal sidecar concept (not a new accepted global schema) links:
- variant ID / parent actor source & pinned source blob;
- existing native config file/ref and SHA, target actor ID;
- operation ID / authoritative tool owner / applied field or donor geometry ref;
- before/after preview or screenshot refs, validation tool/variant, dependencies;
- user-visible status DRAFT / VISUAL_PROVEN / ROUNDTRIP_VERIFIED / CONSUMER_ACCEPTED, with specific error text;
- optional future learner evidence, inventory ref, and undo snapshot.

Validation:
1. before image on actual KFB actor and exact source;
2. after image of same actor/camera showing actual change;
3. export/save confirmation including file SHA;
4. cold close/reopen and import exact exported actor profile;
5. new render equals previously recorded after state, with no duplicate donor eye, no geometry/material regression;
6. revert baseline; confirm other actors/defaults unaffected;
7. if no actual direct cross-Site API, manual file download+import is an honest intermediate, but cannot be described as seamless God Mode persistence.

### Phase D · REAL NOSE/BROW GRAFT (next only if B/C pass)

Existing measured `kfb.nosegraft/1` + `kfb.browgraft/1` in `facegraft.v1.js` use **real CapsuleCarl source geometry** anchored to `EyeRig.eyeFrame()` and head surface probe. Test with current target actor geometry; avoid donor-scale assumptions. Verify clipping, texture, head motion, rotate and restore; no automatic universal nose/mouth replacement.

### Phase E · LATER WORLD CONSUMPTION

A verified `ActorVariantReceipt` can be proposed to existing Player/Resident authoring and Asset Registry consumers. Applying it to a Resident, equipping via Backpack, consuming Fluff or promoting to Stage are **different owner-mediated transactions**, not consequences of pressing Save. Player customization must leave NPC source truth unchanged unless explicitly targeting that NPC. God Mode is World editor consumer only after the current World architecture/human gate is authorized.

## One action, three presentations (same owner)

- GOD MODE: author chooses source and target, Stage candidate, validates cross-owner state;
- MAKER MODE: limited actor selection and safe subset of tool operations; reward/cosmetics later;
- TUTOR MODE: permits same bounded change, asks one question, records independently observable evidence;
- SINGLE TRANSACTION OWNER: current specialist tool handles native config and validation; World/Asset/Inventory only consume postvalidation refs.

## Compatibility and failure cases

- If native Studio v17 loose sources are missing, do not rebuild them from standalones without deterministic extraction/source tracing.
- Head-zone colors ≠ donor-geometry swap. Mouth asset and viseme retargeting remain separate unverified gates.
- Browser private GPT Sites can block automation, cross-origin communication or asset fetching; never invent direct API integration.
- One scene/render owner: preview via current tool, not a second editor WebGL context inside World.
- Source license, actor rig family, geometry ownership and asset provenance must be attached to receipt before release.
- Revertability and no global mutation are hard requirements.
- World R4 STOP / four-island visual A/B remain binding; this proposal does not authorize R5.
