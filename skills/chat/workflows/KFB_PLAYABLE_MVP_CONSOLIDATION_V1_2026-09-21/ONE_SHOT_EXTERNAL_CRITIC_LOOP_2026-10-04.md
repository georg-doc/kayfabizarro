## Purpose

This adapts the high-discipline builder/critic loop used in strong autonomous game-production prompts to KFB.
Technical checks may be green while the actual product is visibly wrong. The critic loop is therefore an **internal continuous quality loop inside the One-Shot**, not a user-facing micro-slice sequence.

## KFB adaptation

- Architecture-first means reconcile and obey existing SSOTs/owners; do not invent replacement architecture.
- AAA means release-quality fidelity to the **KFB claymation / Playmation / living-toy target**, not photorealism.
- Current accepted KFB visual/source references are the primary benchmark.
- Multi-agent fan-out is internal only; **one integration writer** owns the receiving branch.
- Module showcases/source-isolation views are evidence, not Georg-facing gates.
- Final product quality is judged in the integrated world, not by averaging isolated technical PASSes.

## Roles

### Integrator / Builder

The Integrator is the only writer to the receiving runtime/core branch. It consumes accepted owners and pinned donors, implements the integrated product, owns seam repair, keeps the runtime loadable, persists checkpoints, and **automatically continues after green internal checkpoints**.

It may not stop merely because one Player, Resident, Drive, Site or other internal checkpoint passed.

### Module builders · optional internal fan-out

When supported, bounded subagents may work on existing subsystem folders. They may not create a second runtime owner, competing world/movement/audio/editor implementation, or Georg-facing gate. Core changes return to the Integrator. If subagent orchestration is unavailable, the Integrator performs the same sequence itself.

### Independent External Critic

The Critic writes **no production code**.

For WB2 this is a **true fresh-context critic process/agent**, not the Builder changing hats.

It receives only:
- candidate URL/build/head identity;
- fixed rubric;
- accepted KFB/KayKit reference stack;
- source manifest/firewall sufficient to detect substitution.

It does **not** receive:
- Builder transcript/reasoning;
- Builder self-score;
- Builder screenshots as its sole visual basis;
- ranked repair list before its own review.

The Critic opens the actual candidate itself, waits for ready, drives the normal product input path, and captures its **own screenshots and continuous video**. Builder-provided evidence may be cross-checked afterwards, but never substitutes for critic-owned visual/runtime evidence.

Persist:
- critic session/agent identity;
- exact critic prompt;
- candidate head inspected;
- screenshots/video/log filenames;
- raw scores/verdict.

If fresh-context separation or real product access is unavailable:
`CRITIC_NOT_RUN`.

That state is **not equivalent to PASS** and cannot be converted into Georg-facing QA by asking Georg to debug the candidate.

It returns numeric scores, PASS/FAIL per dimension, ranked issues by product impact, exact evidence, source-contamination findings and one repair order. It must never inflate a score because CI is green.

### Whole-Game Critic

Before final Stage publication, a separate whole-game review evaluates the complete Golden Journey and free-roam world as one product. Module scores are insufficient.

### Blind comparator

For taste-sensitive comparisons, an independent judge may receive shuffled A/B pairs: candidate vs previous candidate, candidate vs accepted KFB target, or source object vs integrated/adapted object. This is internal evidence and never replaces Georg's final product judgment.

## Verification harness before more feature work

At the beginning of the resumed One-Shot, establish or extend one deterministic browser verification harness that can launch the actual integrated app, wait for an explicit ready marker, use fixed seed/state, select named camera/world/time presets where supported, capture PNG screenshots and a JSON evidence log, record the exact build/head, console/page/network errors, FPS/frame time, draw calls where available, actual loaded/rendered visible source families, key runtime owners, and Golden Journey checkpoints.

Do not build a parallel debug product. The harness consumes the real product route/states.

## Mandatory source-isolation evidence

For every new visible source family that materially defines a world:
1. show the original source object/family unchanged;
2. show the same source after KFB clay/presentation adaptation;
3. show close roof/facade/base evidence proving source identity survived;
4. show the integrated world view.

A loaded URL, donor name in code, or green loader test is not proof that the intended design survived integration.

## Critic dimensions · 0–10

Scale: 10 = target-defining; 8.5 = release-quality KFB candidate with nits; 7 = good but visibly unfinished prototype; 5 = technical demo/programmer-art territory; below 5 = product-invalid/wrong foundation.

Score independently:
1. **SOURCE_FIDELITY** — intended source survived; no rejected legacy visible family; isolation evidence is convincing.
2. **KFB_VISUAL_COHERENCE** — clay/Playmation/material/light/shadow language; no generic substitute aesthetic.
3. **WORLD_IDENTITY_AND_BIOGRAPHY** — Town/Dystopia/Utopia/Protopia read as distinct authored places rather than bags of props.
4. **COMPOSITION_AND_LIVINGNESS** — strong first frame, depth, motion, Residents, landmarks, ambient life.
5. **PLAYER_MOVEMENT_CAMERA_INTERACTION** — coherent movement/camera/interaction feel; Ground/Drive does not feel stitched.
6. **RESIDENT_CARD_CHATTER** — Residents read as characters/activities; Card/ChatterBox is understandable and canonical.
7. **AUDIO_PERFORMANCE_FEEL** — one audio transport; coherent biome/diegetic transitions; key performance beats work.
8. **TECHNICAL_HEALTH** — no unexplained page/console errors, duplicate owners, unsafe save/resume; acceptable perf.
9. **GOLDEN_JOURNEY_AND_PERSISTENCE** — full reference journey plus fresh-session import/resume works.

## Pass rule

An internal subsystem may remain incomplete while later phases are still being built. But anything claimed complete is not accepted if its critic score is below **8.5**, SOURCE_FIDELITY fails, a CORE blocker exists, unexplained errors remain, or required visible evidence is missing.

Before final Stage publication:
- all REQUIRED_CORE dimensions are implemented;
- no critical dimension is below **8.0**;
- product-weighted critic result is at least **8.5**;
- SOURCE_FIDELITY PASS;
- TECHNICAL_HEALTH has zero unexplained page/console errors;
- Golden Journey + fresh-session import PASS.

No score can override an explicit Georg HUMAN FAIL.

## Repair loop

For a failed critic round: rank issues by product impact; repair shared causes rather than symptoms; regenerate actual-runtime evidence; have the independent Critic review again.

KFB repair budget remains **two repair passes on the same blocking seam**. After two non-improving passes: CORE blocker → freeze + failure-recovery export; optional/minor → quarantine/defer and continue. Do not spend four rounds polishing the wrong foundation.

Only a whole-game PASS proceeds to the integrated human Stage candidate.

### Publication / human-handoff firewall

A successful deploy, Site update, archive hash match, CI PASS or offline screenshot set does **not** make the candidate human-ready.

Before routing the candidate to Georg:
- module critic(s) must have run in fresh context where required;
- Whole-Game Critic must have opened and driven the real product itself;
- critic-owned screenshots/video must exist;
- no required score may be below threshold;
- no browser/tool-policy blocker may be silently replaced by Georg as the tester.

If critic/browser access is blocked:
`INTERNAL_QA_BLOCKED` → preserve candidate → do not promote to Georg-facing acceptance.
